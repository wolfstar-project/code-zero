The dashboard is the single deployable artifact: one Nuxt app serving the UI, the control plane, and authentication from one origin.

## Build and run

```bash
aube run build
node apps/web/.output/server/index.mjs
```

`nuxt build` emits a self-contained `.output/` bundle — no `node_modules` needed at runtime. The server listens on port 3000 by default; override with `PORT`.

## Production checklist

- [ ] **Session secret** — set `NUXT_BETTER_AUTH_SECRET` (this exact name; the development fallback is ignored in production). Generate with `openssl rand -base64 32`.
- [ ] **Postgres** — point `DATABASE_URL` at a managed database and apply the schema once with `aube run db:migrate`. See [Database](/guide/database).
- [ ] **Auth policy** — decide `AUTH_ENABLE_SIGNUP`, the OAuth credentials, organization flags, and the mail-backed flows; they are read at server start, so a change needs a restart. Set `NUXT_PUBLIC_SITE_URL`, which passkeys are bound to. See [Authentication](/guide/authentication/overview).
- [ ] **Mail** — configure Resend (`RESEND_API_KEY`; `MAIL_PROVIDER=resend` is optional) or set `MAIL_PROVIDER=smtp` with its SMTP variables. With neither, `console` only logs. Required if invitations or organizations are enabled. See [Mails](/guide/mails).
- [ ] **Control plane** — issue bearer tokens via `CODE_ZERO_CONTROL_PLANE_TOKENS`, add the repositories `tasks.create` may target from the dashboard (they are rows in the store), and grant modes via `control_plane.modes` in `config.yml`. Without a token, mutations are rejected. See [Protect endpoints](/guide/api/protect-endpoints).
- [ ] **Webhooks** — set `GITHUB_WEBHOOK_SECRET` and `CODE_ZERO_CHECKOUT_PATH`; the webhook route fails closed (503) until both are set. Configure the webhook on the source-control side per [Source-control providers](/reference/source-control-providers).
- [ ] **Isolated execution** — production runs that write require `runner.isolation: container` in repository policy, with an image and resource limits. The included `LocalRunner` is for trusted local development only. See the [Safety model](/guide/safety).
- [ ] **Deployment settings** — set `CODE_ZERO_EDITION` (`self-hosted` unless this is the managed service) and choose `CODE_ZERO_SETTINGS_SOURCE`: `file` reads the limits from `config.yml`, `dashboard` lets an admin edit them at `/settings`. Invalid settings refuse every run. See [Deployment settings](/guide/settings).
- [ ] **Model provider** — select the provider in repository policy and set its credential environment variable. See [Model providers](/reference/model-providers).

## Task history storage

Task history uses the ViteHub KV Runtime Helper: filesystem-backed `fs-lite` by default (`.data/kv`), with Deno KV or Upstash available as driver configuration without touching application code. On Cloudflare Workers it uses a Workers KV namespace bound as `KV`, through the same contract. Records are redacted before they are written.

## Cloudflare Workers

The managed cloud runs the dashboard as one Worker. Build it with the Cloudflare target and deploy the merged configuration:

```bash
VITEHUB_HOSTING=cloudflare aube exec --filter @code-zero/web nuxt build
npx wrangler deploy --config apps/web/.output/server/wrangler.json
```

`apps/web/wrangler.jsonc` holds the bindings, and the build merges it into `.output/server/wrangler.json`:

- **`HYPERDRIVE`** — Cloudflare's pool in front of Postgres. Create it with `wrangler hyperdrive create --connection-string=...` and turn query caching off (`--caching-disabled=true`): sessions and permissions must never be read from a cache. A Worker opens a new database client for every request, because a connection cannot outlive the request that opened it.
- **`KV`** — the task-history namespace.
- **`EMAIL`** — the `send_email` binding for transactional mail, selected by `MAIL_PROVIDER=cloudflare`. Onboard the sender domain in Cloudflare Email Service first. See [Mails](/guide/mails).
- **`MAIL_INBOUND_FORWARDS`** (secret) — where mail for the cloud's own addresses is forwarded through Email Routing. See [Receiving mail](/guide/mails#receiving-mail-on-the-managed-cloud).
- **Secrets** — `wrangler secret put NUXT_BETTER_AUTH_SECRET`, plus the model provider's key and the mail credentials. They are read as environment variables.

Two things differ from a self-hosted deployment. The poller does not run, because a Worker is frozen between requests; webhooks are the way work arrives until a scheduled trigger replaces it. Subscription model providers (`claude-code`, `codex-cli`) are not available, because they drive a CLI on the host.

The **Deploy dashboard** workflow builds and deploys the Worker, and can apply the schema first (`migrate`). It runs on demand, and needs the `CLOUDFLARE_API_TOKEN` secret, the `CLOUDFLARE_ACCOUNT_ID` variable, and a `DATABASE_URL` secret for migrations.

## Hosted sandboxes

For hosted execution, the provider-neutral `RunnerPool` supports vendor adapters (ViteHub, Cloudflare Sandbox, Vercel Sandbox were evaluated — see [Sandbox providers](/reference/sandbox-providers)). Quota checks run before provisioning, leases are bounded, and expired sandboxes are stopped.

## Rebuild triggers

Rebuild the app whenever you change:

- the `BETTER_AUTH_*` hosted-infrastructure variables (they decide which client code ships; every other auth variable needs only a restart);
- anything in `packages/*` (the server bundle inlines them).

## Vercel

`apps/web` ships its own `vercel.json` so it can be deployed as a Vercel project with **Root
Directory** set to `apps/web`: the install and build commands `cd` back to the workspace root
so aube and Turborepo resolve the monorepo correctly.

The build command sets `NITRO_PRESET=vercel`. `nuxt.config.ts` registers `vite-hub/nuxt` with a
deployment preset, and that preset pins Nitro's own, so the build target is a deliberate choice
rather than something Nitro auto-detects: without that variable every build emits the self-hosted
`node-server` bundle in `.output/`, which Vercel cannot serve — it fails with _No Output Directory
named "dist" found_. With it, `config/env.ts` resolves the `vercel` preset and the build writes
`.vercel/output` (Vercel's Build Output API) instead. `VITEHUB_HOSTING` selects the same target and
takes precedence.

Because they select the target, `NITRO_PRESET` and `VITEHUB_HOSTING` are declared on the app build
tasks in `turbo.jsonc`: Turborepo's strict environment mode hides a variable a task does not
declare (`NITRO_*` is forwarded by its Nuxt framework inference, `VITEHUB_HOSTING` is not), and
declaring them keeps the target in the cache key so a self-hosted build is never restored into a
hosted one. Both `.output/**` and `.vercel/output/**` are listed as build outputs for the same
reason.

On a hosted preset the KV Runtime Helper resolves the host's own driver rather than the filesystem
one, because a serverless function has nowhere durable to write: on Vercel that is Upstash, so set
`KV_REST_API_URL` and `KV_REST_API_TOKEN` or task history fails at runtime. See
[Database](/guide/database).

::warning
**Upstream version mismatch**

`vite-hub@0.0.3`'s `vercel` plan checks for a server function at
`.vercel/output/functions/__server.func/index.mjs`, while the installed `nitropack@2.13.4` emits —
and routes to — `__fallback.func`. The bundle is correct; only the name ViteHub looks for is not,
so `nuxt.config.ts` links that name to the emitted function for the length of the check and removes
the link afterwards. That bridge is registered as a Nitro **module**, not under `nitro.hooks`: a
handler placed there replaces the preset's own handler for the same hook, and the `vercel` preset
writes `config.json` and every `.vc-config.json` from its `compiled` hook — without them the
directory exists but Vercel cannot read it, and the build fails with the same missing-`dist` error.
Delete the module and `viteHubVercelEntryName` in `config/env.ts` once a ViteHub release
expects the preset's own layout.
::

`apps/marketing` sets `NITRO_PRESET` the same way. It composes no ViteHub integration, so the
variable only picks its Nitro preset, and it has no KV store to configure.

## Marketing and documentation sites

`apps/marketing` and `apps/docs` are not deployed with the dashboard. Production runs them as two
static Cloudflare Workers, `code-zero-marketing` on `code-zero.dev` and `code-zero-docs` on
`docs.code-zero.dev`. Both are generated ahead of time with `nuxt generate`, and each app's
`wrangler.jsonc` only uploads `.output/public`: no script runs at request time, so there are no
bindings or secrets on the Workers themselves. Unknown paths get the generated `404.html`, and a
trailing slash redirects to the canonical URL without one.

The `deploy-sites.yml` workflow builds and deploys both on every push to `main` that touches them,
and on manual dispatch. It needs two repository settings:

- the `CLOUDFLARE_API_TOKEN` secret, a token limited to **Workers Scripts: Edit** on the account and
  **Workers Routes: Edit** on the `code-zero.dev` zone;
- the `CLOUDFLARE_ACCOUNT_ID` variable.

To deploy by hand, generate the site and run `wrangler deploy` from its directory:

```bash
aube exec turbo run build --filter='@code-zero/marketing^...'
cd apps/marketing
MARKETING_SITE_URL=https://code-zero.dev MARKETING_DASHBOARD_URL=https://app.code-zero.dev aube exec nuxt generate
npx wrangler deploy
```

The Docus prerender needs more memory than Node's default heap, so give `nuxt generate` in
`apps/docs` about 2.5 GB (`NODE_OPTIONS=--max-old-space-size=2560`) or more.

Each app also keeps its `vercel.json`, which the preview deployments on pull requests still use.
