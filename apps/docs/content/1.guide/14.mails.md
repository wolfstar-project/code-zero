`packages/mail` owns transactional email: [Maizzle](https://maizzle.com)-based templates plus a small provider layer. The dashboard uses it for organization invitations and other auth-driven messages.

## Providers

`MAIL_PROVIDER` selects the transport. When it is absent, a configured `RESEND_API_KEY` selects Resend so hosted integrations such as Vercel's work without a second selector variable. With neither set, the default is `console`, which logs instead of delivering — an unconfigured deployment cannot silently attempt real delivery. An explicit `MAIL_PROVIDER` always wins.

| Provider     | Configuration                                                                              |
| ------------ | ------------------------------------------------------------------------------------------ |
| `console`    | None. Logs the rendered message. The credential-free default; not for production.          |
| `resend`     | `RESEND_API_KEY`                                                                           |
| `smtp`       | `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SECURE`                      |
| `cloudflare` | A `send_email` binding named `EMAIL` on the Worker. No variables. Cloudflare Workers only. |

`MAIL_FROM` sets the sender address for every provider.

`SMTP_SECURE` selects implicit TLS: `true` on port 465, `false` on port 587 (STARTTLS).

### Cloudflare Email Service

The managed cloud sends through [Cloudflare Email Service](https://developers.cloudflare.com/email-service/) instead of an API key. `apps/web/wrangler.jsonc` binds it as `EMAIL` and sets `MAIL_PROVIDER=cloudflare`, and the provider calls `env.EMAIL.send()` with the same rendered HTML and plaintext every other provider receives.

Two things sit outside the repository:

- the sender domain in `MAIL_FROM` must be onboarded and verified in the Cloudflare dashboard under Email Service, otherwise every send fails with `E_SENDER_DOMAIN_NOT_AVAILABLE` or `E_SENDER_NOT_VERIFIED`;
- the binding exists only inside a Worker, so selecting `cloudflare` anywhere else, or on a Worker deployed without the binding, fails at the first message rather than falling back to another transport.

A refused message rejects with the service's error code (`cloudflare email rejected the message: E_RECIPIENT_NOT_ALLOWED`), never with the recipient or the body.

### Receiving mail on the managed cloud

The managed cloud also receives mail for its own addresses (`support@`, `security@`, and so on) through [Email Routing](https://developers.cloudflare.com/email-routing/). The Worker forwards each message to an address you choose and refuses everything else; it never reads the body.

`MAIL_INBOUND_FORWARDS` maps aliases to destinations, as `alias@example.com=destination@example.net` entries separated by commas, semicolons, or whitespace:

```bash
npx wrangler secret put MAIL_INBOUND_FORWARDS
# support@code-zero.dev=owner@example.net,security@code-zero.dev=owner@example.net
```

It is a secret rather than a variable in `wrangler.jsonc` because the destinations are personal addresses. Setup outside the repository:

- enable Email Routing on the domain, and add a custom address or a catch-all rule whose action is **Send to a Worker** (`code-zero-app`);
- add every destination under Email Routing's destination addresses and verify it, otherwise forwarding fails and the sender gets a refusal.

Matching is on the exact address, ignoring letter case. A message for any other address is refused with `No such recipient`, so a sender learns it did not arrive. A malformed `MAIL_INBOUND_FORWARDS` refuses everything until it is fixed, and the log names the problem without quoting a destination. Logs name the alias and the outcome, never the sender or the destination.

## Templates

Templates are authored with Maizzle and declared in the package's template registry:

- `mailTemplates` maps a `MailTemplateId` to its template file, subject, and context fields;
- `MailTemplateContext` types the data each template needs;
- `maizzle.config.ts` is discovered by Maizzle's own `render()` call by filesystem convention.

Adding a template means adding it to the registry with a typed context, keeping delivery and content concerns separate: providers never know what a template says, and templates never know how mail is sent.

## Compiling templates

Rendering a template runs Maizzle's pipeline — Vue SSR, CSS inlining, plaintext — on top of a Vite SSR server, which needs a bundler with its platform-native binary and a writable working directory. The deployments that send mail are serverless functions with neither, so rendering happens once at build time instead:

```bash
aube run mail:compile
```

That writes `packages/mail/src/util/compiled-templates.json`, which is checked in and bundled into the package. Each template is rendered once per combination of the `conditional` fields the registry declares — the halves a template renders away when empty — with every other field standing in as a placeholder. `sendEmail` then picks the variant its context matches and substitutes the values, escaping them for the HTML part and leaving them bare in the plaintext one.

Run it after editing anything under `packages/mail/emails/`. `aube test` fails when the checked-in artifact no longer matches what the templates render.

## Previewing templates

`apps/mail-preview` wraps Maizzle's dev server around the package's templates:

```bash
aube run mail:preview
```

This serves every template at `http://localhost:3005` with hot reload, rendered against the sample values in `apps/mail-preview/maizzle.config.ts`. The app owns no templates of its own — its `emails/` directory is a symlink into `packages/mail/emails/`, so edits there reload live. Its `build` script compiles every template to static HTML in `apps/mail-preview/dist/`, which CI runs as a template-compilation check.
