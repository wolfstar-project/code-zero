---
title: Deployment settings
---

Deployment settings are the limits every run on a deployment is held to: how many tasks run at once, how long one command may take, which execution modes may start, how much network a run gets, and, optionally, one model and one container sandbox for every repository. They apply on top of each repository's own [`.code-zero.yml`](/guide/configuration), and the stricter of the two always wins.

The dashboard shows them at `/settings`. What that page lets you do depends on the edition and on where the settings come from.

## Editions

The edition is stated in the environment, never guessed from the host:

| `CODE_ZERO_EDITION`     | What it is                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `self-hosted` (default) | You run Code Zero. An administrator sees and, with the dashboard source, edits every setting.                                   |
| `cloud`                 | The managed service. The service fixes the AI provider, sandbox, database, and mail; organizations may only lower their limits. |

A self-hosted install on Cloudflare, Vercel, or any other host is still `self-hosted`. A value other than these two is treated as `cloud`, the locked edition, and every run is refused until it is corrected.

## Choose where the settings come from

A self-hosted deployment has exactly one source, chosen with `CODE_ZERO_SETTINGS_SOURCE` when the server starts:

```bash
# The default: config.yml is the only authority, and the page is read-only.
CODE_ZERO_SETTINGS_SOURCE=file

# Postgres is the only authority, and an administrator edits the settings on the page.
CODE_ZERO_SETTINGS_SOURCE=dashboard
```

| Source           | Where the settings live                                         | The settings page                                                    |
| ---------------- | --------------------------------------------------------------- | -------------------------------------------------------------------- |
| `file` (default) | The `execution`, `model`, and `runner` sections of `config.yml` | Read-only. Shows which file to edit. Edit it and restart the server. |
| `dashboard`      | The `deployment_setting` table in Postgres                      | An administrator edits and saves them. They can be exported as YAML. |

The two never merge. With the dashboard as the source, settings sections still present in `config.yml` are ignored, and the page warns about them. Moving between sources is a restart with a different `CODE_ZERO_SETTINGS_SOURCE`, never something a request can do. To move from the dashboard to the file, export the settings first and paste them into `config.yml`.

Only an account with the admin role can open the page on a self-hosted deployment; anyone else is told so. Reading and saving need a signed-in session: API keys and operator tokens cannot read or change the settings.

## The instance file: config.yml

Code Zero reads `config.yml` from the server's working directory, or the file `CODE_ZERO_CONFIG` names:

```bash
CODE_ZERO_CONFIG=/etc/code-zero/config.yml
```

The old name `code-zero.deployment.yml` is still read when it is the only file present, with a warning to rename it. When both names exist and `CODE_ZERO_CONFIG` names neither, nothing is read and the settings are refused until you keep one.

`config.yml` also holds the control-plane and polling policy (`control_plane`, `poll`); those are read whichever source the settings use. The annotated template is [`config.example.yml`](https://github.com/wolfstar-project/code-zero/blob/main/config.example.yml). A complete settings example:

```yaml
execution:
  # Tasks this deployment runs at once; the rest wait in the queue. 1 to 64.
  max_concurrent_tasks: 4
  # Minutes before one repository command is stopped. 1 to 1440.
  command_timeout_minutes: 30
  # Modes a run may start in. Must include observe.
  allowed_modes: [observe, suggest, fix]
  # The widest network any run may have: none, restricted, or full.
  max_network: restricted

# Optional. Replaces each repository's model choice. The credential stays in the environment.
model:
  provider: anthropic
  name: claude-sonnet-4-5

# Optional. Forces every run this process executes into a container.
runner:
  isolation: container
  engine: docker
  image: ghcr.io/acme/code-zero-runner:1.0
```

| Key                                 | Default                               | Effect on a run                                                                      |
| ----------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------ |
| `execution.max_concurrent_tasks`    | `4`                                   | The scheduler's ceiling for the whole deployment.                                    |
| `execution.command_timeout_minutes` | `30`                                  | Caps the repository's own command timeout. See [below](#the-timeout-is-per-command). |
| `execution.allowed_modes`           | `[observe, suggest, fix, autonomous]` | A run in any other mode is refused before it is recorded.                            |
| `execution.max_network`             | `full`                                | A ceiling: a repository may narrow it, never widen it.                               |
| `model`                             | none: each repository chooses         | `provider` and `name` replace the repository's model.                                |
| `runner`                            | none: each repository chooses         | Forces container isolation with this `engine` (`docker` or `podman`) and `image`.    |

The settings are strict. An unknown key, an out-of-range number, a value that looks like a credential, or YAML that does not parse makes the whole document invalid, with no field quietly falling back to a default. Invalid settings fail closed: no task starts, from the dashboard, a webhook, or the poller, until they are fixed, and the settings page lists every issue with its `$.path`. `observe` cannot be removed from `allowed_modes`, because it is the mode every unrequested run starts in and the one that never writes. `runner` accepts only container isolation: a setting that moved a repository onto the host would be the one place a run ended up less isolated than its own policy asked for.

## Edit the settings from the dashboard

With `CODE_ZERO_SETTINGS_SOURCE=dashboard`, an administrator edits the execution limits, the model, and the runner on the settings page. The inputs show the accepted ranges as hints, but the server checks every value with the same parser `config.yml` goes through; a refused value is reported beside its field. A saved change applies to the next task that starts, and the page shows who saved it and when.

**Export** downloads the settings as `config.yml`, or copies them as YAML. The export never contains a secret: credentials stay in the environment, the settings refuse anything shaped like one, and the export is redacted against the environment's secrets on the way out.

## Managed cloud

On `cloud` the service's own `config.yml` is the only source, and `CODE_ZERO_SETTINGS_SOURCE=dashboard` is refused. The AI provider, the runner and sandbox, the database and storage, and the mail transport are fixed by the service and are not editable. Customers see only whether each one is configured, never a credential, host, or provider name.

The plan's limits are shown read-only and are the ceiling. An organization's owners and admins may set stricter limits for their own organization's tasks:

- max concurrent tasks;
- timeout per command;
- allowed modes, chosen from the plan's.

An empty field uses the plan's value. The server refuses any value above the plan, and takes the lower of the two again on every run, so a plan lowered later still wins. Members see their organization's limits and the effective result, with no control to change them. The organization is the one selected in the sidebar; its membership and role are checked against the database on every request.

## The timeout is per command

`command_timeout_minutes` is how long one repository command may run before it is stopped, and the longest a hosted sandbox lease lasts. It is not a limit on a whole run: a run that executes several commands, or waits on the model, can take longer in total. The page and the API name it accordingly.

## Not available yet

These are not settings today, and the page shows no control for them, because the server has nothing that would enforce one:

- cost budgets, for a deployment, a plan, or an organization;
- a list of commands runs are allowed to execute;
- requiring an approval before a run writes (narrow `allowed_modes` instead);
- an organization-wide two-factor requirement;
- per-organization repository connections and triggers;
- personal notification preferences.
