title: Authentication overview
---

The dashboard UI is protected by [Better Auth](https://better-auth.com), mounted in-process at `/api/auth/**` by [`@onmax/nuxt-better-auth`](https://github.com/onmax/nuxt-better-auth) from `apps/web/server/auth.config.ts`.

## The boundary

Authentication follows the adapter rule at the package level:

- **`packages/auth`** holds the policy: `authBetterAuthOptions` builds the database, policy, and provider options Better Auth needs, and `authCapabilities` derives what the sign-in surface may advertise. It has no HTTP server and no runtime imports, and its `./config` and `./access` subpaths stay free of database dependencies.
- **`packages/database`** owns the store: the Drizzle schema, the connection factory, and the checked-in migrations. It knows nothing about sign-in and must never import `packages/auth` — see [Database](/guide/database).
- **`apps/web/server/auth.config.ts`** composes that policy into the running instance. It is the only route in the app that resolves the connection string (through `packages/database`) and the signing secret, and therefore the only process that opens a connection to Postgres.

`authBetterAuthOptions` deliberately omits `secret`, `baseURL`, and `trustedOrigins` — the Nuxt module resolves those itself and constructs the actual instance, so the two cannot diverge. `createAuth`, which does build a full standalone instance, remains for callers that own their own secret and origin, such as the Better Auth CLI's schema-generation entry point.

## Secrets

| Variable                  | Rule                                                                                                                              |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `NUXT_BETTER_AUTH_SECRET` | Required under this name in production; generate with `openssl rand -base64 32`                                                   |
| `BETTER_AUTH_SECRET`      | Development-only fallback                                                                                                         |
| `DATABASE_URL`            | Postgres connection string, resolved only by `server/auth.config.ts` (the pre-split `AUTH_DATABASE_URL` is still read when unset) |

## Closed by default

Registration and social sign-in are off until you turn them on, so a fresh deployment cannot be signed up for by a stranger:

- `AUTH_ENABLE_SIGNUP=true` enables self-registration at `/signup` (default `false`); with it off, that page shows a closed state, `/login` hides the link to it, and every other method — social providers, magic links, SSO — signs in existing accounts only;
- each social provider requires both halves of its credential — see [OAuth providers](/guide/authentication/oauth).

## Read at runtime

The policy is read when the server starts, not when the app is built. The server publishes what it serves at `GET /api/capabilities` — plain booleans, no credential or origin — and `/login`, `/signup`, and the navigation render from it. Changing a variable needs a restart, not a rebuild, and a page can never advertise a method the server does not serve.

## Methods and account security

| Variable                           | Default | Effect                                                                                                                |
| ---------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------- |
| `AUTH_ENABLE_EMAIL_VERIFICATION`   | `false` | Sends a verification link on sign-up; needs a mail transport                                                          |
| `AUTH_REQUIRE_EMAIL_VERIFICATION`  | `false` | Refuses password sign-in for an unverified address; implies sending the link                                          |
| `AUTH_ENABLE_PASSWORD_RESET`       | `false` | Offers a reset link by mail; resetting revokes every other session                                                    |
| `AUTH_ENABLE_MAGIC_LINK`           | `false` | Passwordless sign-in by mail (single-use, hashed, ten minutes)                                                        |
| `AUTH_ENABLE_TWO_FACTOR`           | `true`  | TOTP with backup codes and 30-day trusted devices, issuer "Code Zero"                                                 |
| `AUTH_ENABLE_TWO_FACTOR_EMAIL_OTP` | `false` | Also delivers the second factor as a mailed code                                                                      |
| `AUTH_ENABLE_PASSKEY`              | `true`  | WebAuthn passkeys, bound to `AUTH_PASSKEY_ORIGIN` or the site URL; off when neither names an origin                   |
| `AUTH_ENABLE_API_KEYS`             | `false` | Organization API keys for CI: `cz_` prefix, stored hashed, 90-day default lifetime, rate limited; needs organizations |

A capability that needs something it does not have — a mail transport, a passkey origin — stops the server at startup with a message that names what is missing and never a configured value. Passwords are bounded at 8–128 characters; Better Auth 1.7 rejects a longer one with `PASSWORD_TOO_LONG`.

Two-factor and passkeys are on by default because they add no way in: enrolling either needs an existing session and the account's password, and nothing changes for an account that never opts in.

## Administration

The app-wide `user.role` belongs to Better Auth's admin plugin, which every deployment registers. An account with the `admin` role may ban and unban accounts, impersonate one (sessions are attributed with `impersonated_by` and last an hour), and grant roles; the control plane asks the same plugin whether a signed-in account is an administrator rather than reading the role itself.

## Enterprise single sign-on and provisioning

SAML/OIDC single sign-on (`@better-auth/sso`, with domain verification) and SCIM provisioning (`@better-auth/scim`, managed per organization) are registered only when the deployment's edition grants the `sso` or `scim` entitlement. Without it their routes do not exist. SCIM also needs `SCIM_CREDENTIAL_HASH_SECRET` (at least 32 characters), the key its bearer credentials are stored as HMACs under.

## SSR and sessions

The dashboard renders with SSR. The session cookie is scoped to the app's own origin, so the server resolves it directly from the incoming request before the first paint — a signed-out visitor never flashes protected content before redirecting.

## Sessions are not control-plane authority

The Better Auth session protects the dashboard UI. The control-plane API (`/rpc/**`, `/api/v1/**`) uses an independent bearer-token scheme — see [Protect endpoints](/guide/api/protect-endpoints).
