---
title: Permissions
---

Code Zero separates three kinds of authority. None of them implies another.

## Dashboard sessions

A Better Auth session grants access to the dashboard UI. Registration is closed unless `AUTH_ENABLE_SIGNUP` is exactly `true`, so who holds a session is an operator decision.

## Control-plane principals

Control-plane mutations require an operator-issued bearer token, with per-principal repository and execution-mode grants:

| Setting                                        | Grants                                           |
| ---------------------------------------------- | ------------------------------------------------ |
| `CODE_ZERO_CONTROL_PLANE_TOKENS` (environment) | Who may mutate at all (`name:token` pairs)       |
| The `repository` table (store)                 | Which repository paths `tasks.create` may target |
| `control_plane.modes` (deployment file)        | Which execution modes each principal may request |

Without a mode grant, a principal is limited to the non-writable `observe` and `suggest` modes. Approval decisions record the authenticated principal's name, never a wire-supplied actor. See [Protect endpoints](/guide/api/protect-endpoints).

## Repository policy

What a run may do to a checkout is decided by the target repository's own `.code-zero.yml` — mode, autofix gates, change-risk classes, and isolation requirements. A control-plane principal can request a mode, but repository policy still has to allow the work, and high-impact changes always require human approval. See [Repository policy](/guide/configuration) and the [Safety model](/guide/safety).

## Organization roles

When [organizations](/guide/organizations) are enabled, membership and roles govern what a signed-in user sees and manages inside the dashboard. Organization authority never extends to the control plane or to repository policy.

| Permission                                 | Owner | Admin | Member |
| ------------------------------------------ | :---: | :---: | :----: |
| `repository: read`                         |  yes  |  yes  |  yes   |
| `repository: write, configure`             |  yes  |  yes  |   –    |
| `task: create`                             |  yes  |  yes  |  yes   |
| `task: approve, cancel`                    |  yes  |  yes  |   –    |
| `policy: write`                            |  yes  |  yes  |   –    |
| `member: invite, remove`                   |  yes  |  yes  |   –    |
| `apiKey: create, revoke`                   |  yes  |  yes  |   –    |
| `billing: manage`, delete the organization |  yes  |   –   |   –    |

The roles also carry Better Auth's own organization permissions, which its endpoints, Better Enrollment, and the API-key plugin check; they are granted in step with the table above. Members are invited with enrollment invitations (`AUTH_ENABLE_INVITATIONS`); the organization plugin's own invitation endpoints are not served.

## Administrators

The app-wide `admin` role is decided by Better Auth's admin plugin. Administrators may ban accounts, impersonate one, and grant app-wide roles, and the control plane grants a signed-in administrator its writable modes after asking the same plugin.
